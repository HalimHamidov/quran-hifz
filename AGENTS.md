# Правила работы Codex в Quran Hifz

Эти инструкции действуют для всего репозитория. Прямые указания пользователя имеют приоритет.

## Начало задачи

- Проверь состояние Git и актуальную ветку. Сохраняй чужие изменения.
- Для создания или расширения материалов суры прочитай раздел README «Стандарт учебных карточек для любой суры», затем только относящиеся к задаче файлы.
- README и текущий код — источник действующих правил. Датированные файлы вроде `CURRENT_COMPACTION.md` содержат исторический контекст; не возобновляй из них старые задачи и публикации без проверки текущего состояния.

## Полный комплект по умолчанию

Когда пользователь просит создать учебные карточки, оформить новую суру или продолжить её учебный материал, сразу реализуй весь комплект в согласованном диапазоне:

1. Отдельная смысловая иллюстрация для каждого аята и читаемый арабский оригинал.
2. Русский перевод с автором и источником, если текст предоставлен или разрешён к размещению; иначе только ссылка «Открыть аят и переводы ↗», без пустого заголовка «Перевод смыслов» и сообщений об отсутствии текста.
3. Отдельное краткое пояснение по проверенному тафсиру ас-Саади со ссылкой и диапазоном источника.
4. Режимы «Карточка / Арабский язык» и шесть разделов: «Слова», «Грамматика», «Формы слов», «Фразы», «Мнемоника», «Таджвид».
5. Таджикские значения всех слов, таджикская сцена для каждого аята, единая цепочка памяти и ссылки на проверенные статьи Vazhaju.
6. Подключение к тренажёру, мобильный вид, навигация и офлайн-материалы.

Не жди отдельных просьб добавить арабский язык, таджикский, мнемонику или тафсир: это уже принятое предпочтение проекта. Подробности и критерии готовности находятся в README. Для узкого исправления ошибки, текста или оформления не расширяй задачу до создания нового комплекта.

## Диапазон

- Соблюдай явно названные суру и аяты; в продолжении задачи используй уже согласованный диапазон.
- Если диапазон не задан, начни с первых пяти аятов или со всей суры, если в ней меньше пяти. Сообщи выбранный диапазон и работай без запроса дополнительного промпта.
- Если прямо запрошена вся сура, охвати всю суру. Не выдавай частичную работу за полную.
- Не создавай картинки или уроки для аятов за пределами задания. При восстановлении сначала ищи существующие материалы в файлах, ветках и истории.

## Проверка содержания

- Арабские аяты и отдельные слова выводи из `data/ayahs.json`; не перепечатывай и не нормализуй огласовки. Используй `splitBasmala` из `assets/js/arabic.js`.
- Сохраняй предоставленный перевод дословно, включая скобки, сноски и совместные диапазоны. Перевод, пересказ тафсира, языковой пример и мнемоника должны быть подписаны раздельно.
- Пословную морфологию сверяй с Quranic Arabic Corpus. Таджикские словарные основы проверяй в Vazhaju до пометки «проверено»: значение, арабское/персидское написание, часть речи и омонимы.
- У каждого таджикского значения указывай ссылки на соответствующие словарные основы; у мнемоники различай подтверждённый общий корень, смысловую ассоциацию и звуковую подсказку. Не подменяй арабское произношение таджикским.
- Не выдумывай словарные статьи, источники, цитаты или подтверждение проверки. Если источник недоступен, продолжай независимую работу, обозначь неподтверждённое место и ограничение; не публикуй его как проверенное.
- Изображения — условные опоры памяти. Не изображай Аллаха, пророков и ангелов; не генерируй текст Корана внутри картинки. Следуй `docs/AYAH_VISUAL_PROMPT.md` и `docs/RIGHTS.md`.

## Реализация и завершение

- Используй действующие образцы сур 73 и 74, общие модули и относительные пути; не копируй вслепую номера, тексты, источники и правила другой суры.
- Не меняй формат прогресса, не дублируй счётчики и не трогай `surahs/067-al-mulk/legacy/` без отдельной задачи.
- При изменении приложения обновляй ресурсы service worker, версии изменённых URL и кеша, `VERSION`, `CHANGELOG.md` и описание возможностей. Для правок только документации не меняй версии приложения и кеша.
- Проверяй diff, соответствие диапазону, источники и ссылки. Для кода и данных выполняй `npm test`, проверку Tanzil и нужные проверки интерфейса из README. Для документации достаточно проверки ссылок, согласованности и `git diff --check`.
- Публикация требует разрешения пользователя; просьба внести изменения в боевой сайт или уже данное разрешение в текущей задаче учитываются. Эти правила сами по себе не разрешают будущие публикации.
- Если публикация входит в задачу, дождись успешного workflow и проверь реальные страницы и файлы GitHub Pages. Локальная проверка не доказывает публикацию.
